# Intro

Мы разрабатываем веб приложение помогающие участникам записываться на мероприятие "берлинский джем".
(Логотип, ассеты и фирменный стиль пока отсутствует берем стандартное оформление из mantine ui).
Через приложение люди могут предлагать к исполнению песни, а так же бронировать музыкальные роли в предложенных песнях: например я предлагаю песню "Белые Розы" и хочу быть вокалистом.
Песни, выполнившие условие готовности состава, получают зеленый статус и будут исполнены на следующем джеме. Если заполнены все заданные места, песня получает фиолетовый статус. Правила описаны в [статусах песен](/spec/participate/statuses.md).

Рабораем по принципу mobile first но и про десктоп не забываем

Стек: 
– mantine ui + react на фронте + typescript + виртуализация (для больших списков) + awaijs для реактивности
– бекенд на cloudflare workers + D1

Авторизация будет проходить через телеграм и описана в файле [spec/telegram-auth-spec.md](telegram-auth-spec.md)

В качестве API будем использовать deezer

Доступ к приложению появляется после авторизации при наличии username, подтвержденного Telegram. Если username отсутствует, все разделы недоступны: пользователь должен задать username в Telegram и повторно войти. Подробности: [правила доступа](/spec/telegram-auth-spec.md#требование-приложения-к-telegram-username).

Основной UI принцип - не делать кнопку disabled, а давать возможность нажать на нее.
Если функционал не доступен - показывать всплывающее сообщение об ошибке что именно не так.

## Описание работы приложения:
Одновременно запись открыта не более чем на один джем. Во всех пользовательских разделах «ближайший» и «следующий» джем обозначают одно и то же текущее событие для предложений песен и записи на музыкальные роли. Параллельная запись на другие джемы недоступна.

Администратор вручную открывает запись на джем и вручную завершает его. Открытие следующего джема — отдельное действие; завершение текущего не открывает следующий автоматически. Дата и время события сами по себе не завершают джем и не переключают запись на другой.

Если запись еще не открыта ни на один джем, предлагать песни и записываться на роли нельзя. При попытке такого действия показывается сообщение «Запись на следующий джем пока не открыта».

## Кодстайл
Всегда думать о maintainability и scalability.
Использовать atomic design методологию (Atomic Design Methodology Atoms, molecules, organisms, templates, and pages)
Dummy components компоненты должны быть построены с таким уровнем абстракции, что бы не быть привязанными к каким-то частным кейсам использования, не должно быть пропсов которые покрывает какой-то частный кейс, пропсы должны быть достаточно абстрактными и  общеми для dummy components
Пользоваться правилом композиции из более маленьких функций и компонентов, но не мельчить, а использовать тогда когда в этом есть смысл

Везде где я пишу значение может быть undefined - предполагается что значение может быть не задано. Я пишу undefined только потому что мне так проще, т.к. это то что есть на фронте, однако если говорить о проектировании базы данных, то следует использовать нативные значения той базы данных которую мы используем (обычно это null).
Если это null в базе, то наверное и на фронте стоит использовать null для консистентности.

## Асинхронность и websockets
Множество людей могут одновременно заполнять музыкальные роли одной и той же песни - это должно корректно просчитываться, а изменения должны быть мгновенно видны всем пользователям
