# Спецификация модуля авторизации через Telegram

## Цель и границы

Реализовать независимый модуль `telegram-auth`, который обеспечивает вход через Telegram, создание сессии и проверку текущего пользователя. Подключение к веб-приложению — через HTTP-маршруты и серверную функцию `requireAuth()`.

Использовать официальный Telegram Login через OpenID Connect: Authorization Code Flow с PKCE.

Модуль получает настройки и адаптер хранилища через параметры подключения и не зависит от бизнес-логики приложения. Его маршруты доступны на одном домене с веб-приложением. Решения о ролях и доступе к конкретным ресурсам принимает приложение.

## Блокирующие зависимости

Эти шаги необходимо завершить до проверки реального входа через Telegram. Разработку модуля и автоматические проверки с тестовым провайдером можно выполнять до их завершения.

1. **Подготовить адрес приложения.** Определить HTTPS-домен и полный URL callback, например `https://example.com/auth/telegram/callback`. Для сквозной проверки сервер должен обслуживать этот адрес.
2. **Создать бота через BotFather.** Задать название и аватарку сервиса. Бот представляет приложение в процессе входа; обработка сообщений для авторизации не требуется.
3. **Зарегистрировать разрешённые URL.** В настройках входа бота указать адреса приложения и точный URL callback.
4. **Получить параметры подключения.** Получить `Client ID` и `Client Secret` в BotFather и передать их в серверную конфигурацию. Секрет должен быть доступен только серверу.

Источник: [настройка Telegram Login](https://core.telegram.org/bots/telegram-login#registering-your-allowed-urls).

## HTTP API

| Маршрут | Назначение |
|---|---|
| `GET /auth/telegram` | Начать вход и перенаправить пользователя в Telegram |
| `GET /auth/telegram/callback` | Обработать результат входа и создать сессию |
| `GET /auth/me` | Вернуть текущего пользователя; без действующей сессии — `401` |
| `POST /auth/logout` | Завершить сессию и удалить cookie |

Модуль возвращает приложению минимальный объект пользователя: `id`, `displayName`, `avatarUrl`, `username`. Поле `username` берется из `preferred_username` проверенного ID token. Данные профиля могут отсутствовать; отсутствие username передается как `null`.

### Требование приложения к Telegram username

Приложению нужен действующий Telegram username пользователя. Он должен подтверждаться данными Telegram; ручной ввод сам по себе не подтверждает принадлежность или актуальность username.

После каждого входа приложение проверяет username, полученный из проверенного ID token. Если username отсутствует, все разделы приложения недоступны, включая просмотр, предложения песен, участие и админку.

Вместо приложения показывается экран с объяснением: нужно задать username в настройках Telegram и затем повторно войти через Telegram. На экране доступны повторный вход и выход из учетной записи. Ручной ввод username внутри приложения не предусмотрен. Доступ появляется только после нового успешного входа, в результате которого Telegram передал username.

Ограничение проверяется на сервере для API приложения, а также при открытии страниц. Маршруты авторизации, `/auth/me` и выхода остаются доступны для восстановления доступа. Эти правила относятся к приложению, а не к независимому модулю авторизации: модуль по-прежнему может вернуть `username: null`.

При каждом успешном входе, если username пользователя изменился – username в приложении обновляется, однако если приходит `null` - будет оповещение, чтобы пользователь вернул видимость username. Пользоваться приложением без username нельзя, т.е. в данном случае при username `null` работа приложения блокируется до момента пока пользователь не раскроет username обратно.

## Шаги реализации

### 1. Выделить структуру модуля

Разместить внутри модуля:

- обработчики HTTP-маршрутов;
- интеграцию с Telegram через OIDC-библиотеку;
- управление сессиями и функцию `requireAuth()`;
- интерфейс хранилища пользователей, попыток входа и сессий.

Конфигурация: параметры Telegram, URL callback, адрес страницы после входа и срок сессии. Запрашиваемые разрешения — `openid profile`.

### 2. Реализовать начало входа

- Генерировать `state`, `nonce` и параметры PKCE.
- Временные данные попытки входа связывать с браузером и хранить на сервере.
- Ограничить срок действия попытки и разрешить её использование только один раз.
- Перенаправлять пользователя на страницу авторизации Telegram.

### 3. Реализовать callback

- Проверить соответствие ответа начатой попытке входа.
- Обменять код на токены на сервере.
- Проверить подпись ID token, `iss`, `aud`, срок действия и `nonce`.
- При отказе пользователя или ошибке вернуть его на страницу входа с возможностью повторить попытку.

Источник: [обмен кода и проверка токена](https://core.telegram.org/bots/telegram-login#manual-implementation).

### 4. Связать аккаунт с пользователем приложения

- При первом входе создать пользователя, при повторном — найти существующего.
- Ключ внешней учётной записи — пара `issuer + sub`, сохранённая строками с уникальным ограничением в БД.
- Имя, username и аватар сохранять как необязательные данные профиля.
- При каждом успешном входе обновлять username по проверенным данным Telegram; если он отсутствует, сохранять `null`, а не прежнее значение.
- Username не использовать как идентификатор.

### 5. Добавить сессии

- После успешного входа выдавать новый случайный идентификатор сессии.
- Хранить сессию на сервере, идентификатор — в cookie с `HttpOnly`, `Secure`, `SameSite=Lax`.
- Срок сессии задавать конфигурацией.
- При выходе отзывать серверную сессию и удалять cookie.
- Изменяющие состояние запросы защищать от CSRF.

### 6. Подключить интерфейс и защиту доступа

- Кнопка «Войти через Telegram» открывает `/auth/telegram`.
- После входа приложение получает пользователя через `/auth/me`.
- Закрытые API и страницы проверяют сессию на сервере через `requireAuth()`.
- Адрес возврата после входа ограничивается разрешёнными страницами приложения.

## Критерии готовности

- Первый вход создаёт пользователя; повторный возвращает того же пользователя.
- Отмена, поддельный ответ, неверный `state`, просроченный или повторно использованный callback не создают сессию.
- После выхода или истечения сессии закрытые маршруты возвращают `401`.
- Вход работает в мобильном и настольном браузерах.
- Секреты и токены отсутствуют в клиентском коде и логах.
- Модуль подключается через конфигурацию, адаптер хранилища и маршруты без зависимости от бизнес-логики приложения.

Критерии подключения к приложению:

- При отсутствии username недоступны все разделы и API приложения, даже при действующей сессии; доступны только экран с объяснением и маршруты авторизации, проверки сессии и выхода.
- После задания username в Telegram и повторного успешного входа приложение получает подтвержденное значение и допускает пользователя к своим разделам с учетом остальных правил доступа.
- Повторный вход без username не восстанавливает доступ и не сохраняет прежний username.
